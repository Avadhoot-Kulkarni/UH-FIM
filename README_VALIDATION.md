# UH-FIM Synthetic Dataset and Validation Procedure

This procedure is written for the current UH-FIM implementation in this folder. It does not change the normal `data/baseline.json` or `data/baseline.checksum` files.

## Requirements

- Python 3.10 or newer (the source uses modern type annotations).
- The dataset generation and API validation script uses the Python standard library and should run on Windows, macOS, and Linux.
- The current `uhfim.py` imports the live-monitor module at startup, so install `watchdog` before using its CLI commands: `py -m pip install watchdog` on Windows. (The standalone `uhfim_dataset_eval.py` evaluation does not import the live monitor.)

## Run the complete evaluation

From this folder (the one containing `uhfim.py`, `core/`, `utils/`, and `uhfim_dataset_eval.py`):

```powershell
py -3 uhfim_dataset_eval.py all
```

Or run each stage separately:

```powershell
py -3 uhfim_dataset_eval.py generate
py -3 uhfim_dataset_eval.py validate
```

The generator creates 45 deterministic synthetic fixtures (15 per category), across 4 KiB, 64 KiB, and 1 MiB size bands. Their filenames/extensions deliberately exercise the current `utils/categorizer.py`. They are synthetic byte fixtures, not real operating-system files, private keys, or executable programs. Do not execute them.

## Outputs

Created under `uhfim_evaluation_dataset/`:

- `clean/`: clean 45-file dataset used as the pristine source.
- `manifest.csv` and `manifest.json`: file path, expected/actual category, chosen strategy, size band, size, full-file SHA-256 ground truth, and adaptive hash at generation time.
- `results/validation_results.csv`: each unchanged-control file and each controlled modification scenario.
- `results/validation_summary.json`: confusion-matrix counts and derived metrics for this small test suite.
- `results/benchmark_by_file.csv`: per-file adaptive-vs-full SHA-256 bytes read and median runtime over three runs.
- `results/benchmark_summary.csv`: grouped summary by category and file size.
- `results/evaluation_baseline.json` and `.checksum`: temporary test baseline generated by the project's real `create_baseline()` and `load_baseline()` functions. The script redirects these two files into `results/` so the project's normal `data/` baseline is not overwritten.
- `work/`: working copy used by the most recent test. It may contain the last test mutation; treat `clean/` as the pristine master.

## What is tested

1. Clean baseline: all 45 files left unchanged.
2. Full-hash critical file modification.
3. Change inside one of the executable BLOCK regions.
4. Change outside the executable BLOCK regions (tests a known partial-hash blind spot).
5. Change inside a DATA SAMPLE region.
6. Change outside the DATA SAMPLE regions (tests a known partial-hash blind spot).
7. Addition of a new file.
8. Verification of a deleted, baseline-known file through `verify_file()`.

The script imports and calls the current project's `compute_hash()`, `create_baseline()`, `load_baseline()`, `verify_file()`, categorizer, and risk-scoring functions. It does not test the watchdog event loop or the printed CLI summary; live monitoring must be checked separately.

## How to interpret the measures

- `expected_change=1` means the test deliberately changed, created, or deleted a file.
- `detected_by_uhfim_api=1` means the existing API returned a changed/new/deleted outcome.
- Detection rate/recall = TP / (TP + FN).
- False-positive rate = FP / (FP + TN).
- `adaptive_bytes_read_measured` counts bytes returned by file `read()` calls in the current hasher. It measures algorithmic read volume, not physical disk I/O or cache misses.
- Runtime is machine-, filesystem-, and cache-dependent. Compare multiple repeated runs and report the environment.

The negative probes are intentional. Current BLOCK/SAMPLE hashes do not read every byte of larger files, so a mutation outside the selected regions can yield the same adaptive hash. A missed mutation must be reported as a false negative, not hidden from the results. The synthetic suite is a preliminary controlled test, not proof of production or cloud-scale effectiveness.

## Optional: show the command-line flow manually

The automated harness is safer because it preserves the normal baseline. If you also want to demonstrate the CLI, back up `data/baseline.json` and `data/baseline.checksum` first, then run:

```powershell
py -3 -m pip install watchdog
py -3 uhfim.py baseline uhfim_evaluation_dataset/clean
py -3 uhfim.py scan uhfim_evaluation_dataset/clean
```

These CLI commands use the project's normal `data/` baseline and will overwrite it. Restore your backups afterwards. The scan checks files that currently exist; it does not independently enumerate baseline entries that have disappeared. The current live monitor has a deletion event handler, while the automated test directly checks `verify_file()` for a known deleted path.

## How to present this in the paper

Use the generated CSV files to make plots. Report the exact number of test scenarios, the machine/OS/Python version, repeated-run policy, confusion-matrix metrics, bytes read and runtime. Do not call this dataset a public benchmark: it is an original synthetic dataset created for this controlled evaluation. Do not claim industry superiority based on this experiment alone.
